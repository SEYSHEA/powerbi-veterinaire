Démo prédiction

Un rapport Power BI construit sur des ventes vétérinaires fictives. Il estime le chiffre de fin d'année et signale les cliniques qui risquent d'arrêter de commander, grâce à deux modèles écrits en Python qui tournent dans Power BI.

Objectif

Deux questions, deux publics

Ce rapport répond à deux questions qu'on entend souvent dans une équipe commerciale. La direction veut savoir si l'année finira au-dessus ou en dessous du budget. Les délégués, eux, veulent savoir quelles cliniques décrochent, et laquelle appeler en premier.

Le rapport

Une page pour la direction et pour les délégués

Rapport Power BI exporté en PDF. Données fictives.

  • L'atterrissage additionne les ventes déjà réalisées en 2026 et la prévision du modèle jusqu'à décembre. Il atteint 2 267 698 €, soit 4 % au-dessus du budget.
  • Sur les neuf premiers mois de 2026, le modèle s'est trompé de 2,56 % sur le total, contre 5,84 % pour le forecast. Le forecast étant lui aussi inventé, la comparaison reste indicative.
  • 11 cliniques ont plus de 40 % de chances d'arrêter de commander. Elles ont représenté 80 109 € sur les douze derniers mois.
  • Sur la courbe, le teal suit les ventes réelles et le vert le modèle, entouré de sa marge d'erreur.
  • Le tableau classe les cliniques de la plus à risque à la moins à risque avec la raison principale et le nombre de jours sans commande. C'est la liste d'appels des délégués.

Les données

Six tables fictives

Les produits, les cliniques et les montants sont tous inventés. Le jeu de données a quand même été pensé pour ressembler à un vrai suivi des ventes. On y retrouve le pic des antiparasitaires au printemps, le creux d'août, une croissance d'environ 5 % par an, et des cliniques qui commandent de moins en moins avant d'arrêter.

Les mesures DAX

Elles sont rangées dans une table _Mesures. Voici celles qui font tourner la page.

Gross Sales

Le chiffre d'affaires au prix tarif, calculé ligne par ligne. Presque tout le reste en dépend.

SUMX ( SellIn, SellIn[Quantite] * SellIn[Prix_Tarif_Unitaire] )

Dernier mois complet

La dernière vente enregistrée date du 16 octobre 2026. La mesure prend la fin du mois précédent, le 30 septembre, pour ne garder que des mois entiers. C'est la frontière entre le réel et la prévision.

EOMONTH ( CALCULATE ( MAX ( SellIn[Date] ), ALL ( SellIn ) ), -1 )

EYE modele

L'atterrissage de fin d'année. Il ajoute au cumul réel de janvier au dernier mois complet (CF annee) la prévision du modèle jusqu'à décembre.

[CF annee] + [Prevision fin annee]

Ecart EYE modele vs budget

L'écart entre cet atterrissage et le budget de l'année, en pourcentage.

DIVIDE ( [EYE modele] - [Budget annee], [Budget annee] )

Erreur backtest modele

Ce que le modèle avait prévu pour janvier–septembre 2026, comparé à ce qui s'est vraiment vendu. La même mesure existe pour le forecast.

VAR fin = [Dernier mois complet]
VAR reel = CALCULATE ( [Gross Sales], REMOVEFILTERS ( Calendrier ),
    DATESBETWEEN ( Calendrier[Date], DATE ( YEAR ( fin ), 1, 1 ), fin ) )
VAR prev = CALCULATE ( SUM ( prevision_produit[Prevision] ),
    prevision_produit[Type] = "Backtest", REMOVEFILTERS ( Calendrier ) )
RETURN DIVIDE ( ABS ( prev - reel ), reel )

Reel mois complets

Pour chaque mois du graphique, la mesure compare le dernier jour du mois au 30 septembre. Au-delà, elle ne renvoie rien et la courbe du réel s'arrête en septembre. Sans elle, octobre, à moitié écoulé, ressemblerait à une chute.

IF ( MAX ( Calendrier[Date] ) <= [Dernier mois complet], [Gross Sales] )

Cliniques risque eleve

Le nombre de cliniques que le modèle classe en risque élevé, au-delà de 40 % de probabilité de perte.

CALCULATE ( COUNTROWS ( score_clients ), score_clients[Niveau_risque] = "Élevé" )

CA a risque

Ce que ces cliniques ont acheté sur douze mois, autrement dit la perte possible en euros.

CALCULATE ( SUM ( score_clients[CA_12_mois] ), score_clients[Niveau_risque] = "Élevé" )

Le forecast de ces données a été tiré au hasard autour du budget, donc le modèle part avantagé. Ce qui m'intéressait, c'est la méthode. Sur de vraies données, les chefs de produit savent des choses que l'historique ignore, comme un lancement ou une rupture de stock. Le modèle servirait alors de point de comparaison, pas de remplaçant.

Risque de perte client

Période de test jamais vue par le modèle

Une régression logistique donne à chaque clinique une probabilité d'arrêter de commander dans les six mois. Elle apprend sur des « photos » mensuelles du passé, qui associent ce qu'on savait de chaque clinique à une date donnée et ce qui s'est passé ensuite.

Sur la période de testValeur
AUC0,91
Part de cliniques réellement perdues2,8 %
Part de vraies pertes parmi les 10 % les mieux scorées21 %

Ici, les cliniques qui partent ralentissent toutes avant d'arrêter, ce qui les rend faciles à repérer. Sur de vraies données, le score serait sûrement moins bon, et il gagnerait à intégrer d'autres signaux, comme les visites des délégués.
